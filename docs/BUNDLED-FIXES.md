# Reviewed bundled fixes and migration

Release v0.1.2 carries independently reviewed transferable fixes from a separately validated server into the public resource bundle. It changes no running server. Compose and the English deployment documentation select image 0.1.2. Bundled resources are host-mounted, so update the checkout as well as the image; changing an image tag alone does not update them.

## FixRandomSpawn 1.2.0 included

The public bundle includes the unmodified official [qstage/CS2-FixRandomSpawn v1.2.0 release](https://github.com/qstage/CS2-FixRandomSpawn/releases/tag/v1.2.0), authored by xstage. ZIP SHA-256 is `554e5ebe5fb1046e263ff4745477a7f39c91131332918d342ed6e9f595aaed1b`. Its `plugins/` and `gamedata/` roots are installed relative to `addons/counterstrikesharp/`: the active DLL is `plugins/FixRandomSpawn/FixRandomSpawn.dll` and signatures are global `gamedata/FixRandomSpawn.json`. All six package files are retained byte-for-byte; no cfg or private settings are supplied or overwritten. The official dependency manifest identifies its assembly as `FixRandomSpawn/1.0.0`; the plugin's ModuleVersion is 1.2.0. This upstream metadata is preserved.

The separate original deployment reproduced a bot PRESPAWN crash with 1.1.4 and passed bot spawn checks with 1.2.0. This is prior server evidence, not a new engine test of this fleet. The source enables `mp_randomspawn=1` across modes by default; it can change Competitive/Practice/Retakes spawn behavior. Review the active cfg chain, effective ConVars and generated plugin settings before acceptance; normal spawn behavior is not guaranteed. No old 1.1.4 plugin-local gamedata is bundled.

The tagged source commit `65fb0252a0d020f546b5ee8d34dfef9a31c769bf`, README and project metadata expose no license grant. License metadata is recorded as **unknown**, with the source archive retained for provenance. Inclusion follows the maintainer's explicit instruction; it does not establish a redistribution grant or relicense this component under the fleet's LGPL.

## Preserve saved configuration

The bundled GameModeManager JSON keeps the **34 public mode entries**, their order, default, maps/map groups, warmup and commands. After 0.1.2, the only gameplay default correction is `Rotation.Enabled=true` so GMM owns ordinary match-end map advancement. `ModeRotation`, `ModeSchedules`, `WhenServerEmpty` and `MapChooser.ModesInVotes` remain false; GG1 remains the map voter and immediate RTV handler. GG1 automatic changes and engine automatic changelevel remain disabled. One deliberate correction changes the Casual (1.6) `Config` reference to the existing exact-case `Casual-1.6.cfg`; that cfg’s immediate and map-start settings references likewise use the existing `Casual-1.6_settings.cfg`. It migrates schema 12 → 13, sets WorkshopAddon `3831211166`, maps old RTV time/kill triggers and IncludeModes into MapChooser, and changes the unsupported vote style `center` to `menu`. The old RTV object remains for reference; GMM 2.0.0 ignores it. GG1 now owns RTV, nomination and map voting, so settings such as vote durations, round triggers and extension rules require deliberate review against its new configuration. They do not migrate automatically.

Existing instance cfg/JSON is deliberately retained by `materialize`; fresh bundle defaults do not overwrite saved choices. For an existing fleet:

The public CSS `configs/admins.json` is empty (`{}`); inherited upstream administrator identities are removed. Permission-group definitions remain available. Fresh instances receive no administrators, while existing private admin JSON is preserved by materialization. Import only your own authorized administrator configuration through the private migration procedure.

1. Stop all consuming game processes using the operations procedure. Back up each instance's cfg, addon/config directories, permissions, plugin-local databases and the overlay privately. Keep a copy of the old bundle as well.
2. Stage the reviewed resource tree as the shared overlay; do not unzip release defaults over an instance's cfg. Run the offline helper once for each saved GMM JSON:

   ```sh
   python3 scripts/migrate-menu-config.py data/instances/server1/addons/counterstrikesharp/configs/plugins/GameModeManager/GameModeManager.json --map-change-owner preserve
   ```

   The helper refuses a saved `Rotation.Enabled=false` (schema 12 **or** 13) unless the operator explicitly chooses `--map-change-owner preserve` or `--map-change-owner gmm`. `preserve` retains existing ownership/intentional disabled advancement and emits a warning; it does not establish that an owner exists. `gmm` changes only `Rotation.Enabled` beyond the menu migration. Before selecting it, audit the effective GG1 configuration and cfg chain: disable GG1 `ChangeMapAfterVote`, `ChangeMapAfterWinDraw`, `ChangeMapAfterTimeLimit`, `RandomMapOnStart`, `LastDisconnectedChangeMap` and engine `mp_match_end_changelevel` to avoid competing automatic owners. Keep `ModeRotation`, `ModeSchedules`, `WhenServerEmpty`, mode lists and all unrelated operator values as intended; the helper does not change them. Do not select `gmm` merely because a production vote succeeded: immediate RTV can change maps with all automatic match-end owners disabled. See [source evidence and regression harness](MAP-CHANGE-OWNERSHIP.md).

   The helper refuses unsupported schema/symlink paths and writes an exclusive `.before-panorama` backup (`.before-map-owner` for an ownership repair of an already migrated schema-13 file, preserving its earlier menu backup). It does not migrate GG1 or private allocator config. Run it as the instance file owner; back up first and keep the backup private.
3. Correct the saved Casual (1.6) mode reference to `Casual-1.6.cfg` and its settings exec references to `Casual-1.6_settings.cfg` if they still use lowercase names; the menu migration helper preserves operator mode entries. Review the three new menu configs. Preserve any existing custom menu/chooser settings. Only when deliberately selecting GMM as the match-end owner, apply the ownership switches listed above; retain `wasd` menu modes for the bridge. In each saved allocator `plugins/disabled/RetakesAllocator/config/config.json`, merge the three fallback/pinning keys above without replacing weapon preferences or databases.
4. Ensure no old autoloaded WASD plugin survives in a private overlay. Immutable stale links managed by this runtime disappear; imported regular binaries must be audited separately. Keep MenuManagerApi only under `shared/MenuManagerApi`; refresh any plugin-local GameModeManager.Shared.dll with the matching shared DLL. Preserve other Workshop IDs when adding `3831211166` to saved MultiAddonManager cfg. Allow its download and reconnect clients.
5. Restart against the staged bundle and complete the acceptance checks below. For rollback, stop the fleet and restore the complete consistent old bundle plus private config/database backups. A copied backup is not a tested restore.

`!modes` opens the admin mode menu; `!mode <name>` directly changes a mode and requires an argument. `!menu` selects a player's menu style; new players default to PanoramaMenu.

## Provenance and licenses

[The machine-readable manifest](bundled-baseline.json) records package SHA-256 values, exact source revisions and hashes of staged binaries. [third_party](../third_party/README.md) contains licenses and corresponding source archives beside the distributed bundle. GMM, GG1 and Gameloop.Vdf are MIT; PanoramaMenuManager/MenuManagerApi, PMM bridge and allocator are GPLv3; CSS is GPLv3 with its upstream linking exception. These are separate components, not relicensed under the fleet's LGPL. Existing Metamod and MultiAddonManager are unchanged.

`scripts/update/pins.json` prevents the generic resource updater from replacing this reviewed stack or downgrading a CI pin. A maintainer must review source, API/ABI compatibility, license, package paths, digests and the entire dependency stack before removing/replacing a pin. It does not discover or auto-install arbitrary latest CI builds. The fleet sidecar remains responsible for stop/lock/overlay orchestration; the obsolete single-host scheduler is not activated or imported.

## Acceptance and known limits

The [source-backed C# regression](MAP-CHANGE-OWNERSHIP.md#executable-regression) runs in CI using pinned source archives and an immutable SDK image with no execution-time network. It covers voted-winner advancement, active-vote waiting, overlapping end triggers, disabled rotation, manual mode changes and immediate RTV-style transitions. Offline tests also cover the actual packaged files, their hashes, matching API copies, lookup paths, config migration, pin enforcement and instance materialization. Docker smoke exercises real containers/mounts and process coordination with an offline Steam fixture. These establish package and orchestration behavior; they do not run the CS2 engine.

The separate original deployment provided server-side evidence for CSS/Metamod loading, bot spawn after FixRandomSpawn 1.2.0, allocator fallback, three mode cfgs, menu plugin loading and mounted Workshop resources. It had 32 private modes; those are not copied into these 34 public defaults. No human client rendered/clicked the menu. That evidence is not acceptance of this fleet or all bundled plugins.

Before deployment acceptance, use a real empty CS2 instance and verify native/managed load logs, bot PRESPAWN/spawn/respawn and round transitions, Competitive/Practice/Retakes execution, weapon allocation, Workshop download, a human joining, opening/clicking `!modes`, a second map request and movement after transitions. The original movement-lock defect remains unresolved upstream; the rejected experimental movement binary is excluded. A startup `Global Variables not initialized yet` warning was observed in the original deployment. A generic LOADED string or responsive status is insufficient health evidence. No live restart, game migration or human acceptance was performed by this change.
